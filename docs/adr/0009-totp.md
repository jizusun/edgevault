# ADR 0009: TOTP, in vault items and as a login second factor

Status: proposed

## Summary

"TOTP" means two different things, and the MVP supports both:

1. **TOTP codes stored in vault items.** You save a website's 2FA secret in a login item, and the Bitwarden app shows the 6-digit code. The secret is encrypted by the client like any other field, so the server only stores it. The clients show these codes only to premium users, so the server reports every user as premium.
2. **TOTP as a second factor for logging in to edgevault.** You scan a QR code with an authenticator app, and from then on logging in needs your master password **and** a 6-digit code.

## Decision

### TOTP in vault items

- Nothing special to store; the `totp` field is part of the encrypted item data.
- The profile and sync responses return `premium: true` for every user. This was observed in Vaultwarden's responses, and it is what makes the clients display item TOTP codes.
- A scenario checks that `premium` is true for every user.

### TOTP as a login second factor

- **Setup:** the user asks for a new secret, the client shows a QR code, and the user proves they can generate a valid code. Only then is 2FA turned on. A one-time recovery code is shown once.
- **Login:** the password grant returns a "two-factor required" error listing the available providers. The client sends the password grant again with the code. Exact field names come from M0 traffic capture.
- **Verification:** RFC 6238, HMAC-SHA1, 6 digits, 30-second steps, accept one step before and after for clock drift. Implemented with Web Crypto.
- **Replay protection:** store the last accepted time step per user; a code for that step or an earlier one is rejected.
- **Brute force:** failed codes count in the per-account Durable Object ([ADR 0005](0005-per-account-durable-object.md)), the same as failed passwords. A 6-digit code has only a million values, so this matters.
- **Storage:** the TOTP secret is encrypted at rest in D1 with AES-GCM, using a key in Workers Secrets. A copy of the database alone does not reveal it. (The server must be able to read the secret to check codes, so this protects against a database leak, not against someone who controls the Worker.)
- **Recovery code:** stored only as a hash. Using it turns 2FA off and is logged.
- **Remember this device:** optional; issues a long-lived, purpose-specific token ([ADR 0006](0006-token-signing.md)) that skips the code on that device. Invalidated by a password change or turning 2FA off.

## Testing

- The RFC 6238 appendix test vectors are a table in `specs/`, an independent oracle.
- The `otpauth` library generates codes in tests, so the test client does not share code with the server.
- Scenarios: setup, login with and without a code, wrong code, replayed code, clock drift, lockout after repeated failures, recovery code, remember-device token, and invalidation.

## Not in the MVP

Email, WebAuthn and passkey, YubiKey OTP, and Duo second factors. Email 2FA would need Email Service and is a candidate after the MVP.

## Alternatives considered

- **Store the TOTP secret in plain text**, as some servers do: simpler, but a database export would reveal every user's second factor.
- **Skip login 2FA in the MVP:** less work, but a family vault exposed on the internet should have it.

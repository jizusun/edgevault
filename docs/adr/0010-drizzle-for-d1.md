# ADR 0010: Drizzle as a typed query builder for D1

Status: proposed, bundle size and startup cost to be measured in M0

## Summary

We use **Drizzle** to describe the database tables in TypeScript, write type-checked queries, and generate migration files. A renamed column or a wrong type then fails the build instead of a test.

We use it as a **query builder only**, not its higher-level "relational queries". The two most sensitive queries, sync and the organization access checks, are written as reviewed SQL inside Drizzle. The budget tests still measure every query, so a slow query is caught whoever wrote it.

## Context

- The data model has about 13 tables, and the organization tables need joins where a mistake could leak items between family members ([ADR 0008](0008-organizations.md)).
- Drizzle has a D1 driver that uses the binding directly ([docs](https://orm.drizzle.team/docs/sqlite/connect-cloudflare-d1)), and supports D1's batch API, which sends several statements in one call ([docs](https://orm.drizzle.team/docs/sqlite/batch-api)). Batches keep us under the Free plan's 50 queries per request.
- `drizzle-kit` generates SQL migration files that `wrangler d1 migrations apply` can run.
- The first version of this design said "no ORM", because an ORM hides the exact SQL. That objection is weaker than it looked: our budget tests read D1's own `rows_read`, `rows_written`, and query counts, so they catch an expensive query however it was produced.
- Versions in November 2026: `drizzle-orm` 0.45.4, `drizzle-kit` 0.31.11. It is not 1.0 yet.

## Decision

- Schema in `src/adapters/d1/schema.ts`, the single source of truth for tables and indexes.
- Queries through Drizzle's query builder, inside the D1 adapters only. The domain and application layers never import Drizzle (enforced by dependency-cruiser).
- Sync and the organization access checks are written with Drizzle's `sql` template (parameterized) and reviewed like security code. Each has a budget scenario.
- No relational query API (`db.query.*`) in the MVP. It generates SQL we do not see in review.
- `sql.raw()` and string-built SQL are banned by a Semgrep rule.
- Migrations are generated by `drizzle-kit generate`, then reviewed and committed. A CI check rejects `DROP` and `RENAME` in the same release as the code that stops using them, so migrations stay additive.
- Bulk inserts are chunked by our own helper to stay under D1's 100 bound parameters per statement; Drizzle does not do this for us.
- Exact versions are pinned. Upgrades are their own PR, with the full suite and the budget tests.

## Consequences

- Type errors in queries fail at compile time.
- Generated migrations save effort but still need a human to read them.
- Pre-1.0 upgrades may require changes; pinning and dedicated upgrade PRs keep that controlled.
- M0 measures the bundle size and cold-start cost with Drizzle included, because the Free plan allows only 10 ms of CPU per request. If the cost is significant, we fall back to plain SQL behind the same adapter interface.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Plain SQL with small typed helpers (previous plan) | No compile-time check of column names and types across 13 tables |
| Kysely with `kysely-d1` | Good typed query builder, but `kysely-d1` was last updated in April 2025 |
| Prisma with `@prisma/adapter-d1` | Heavier runtime and generated client; more than we need |
| Drizzle relational queries | Hides the generated SQL for the queries where we most need to see it |
